# CS-30 第一周分工安排（保守版）

**项目：** Personalised AI Learning Assistant using Retrieval-Augmented Generation and Large Language Models  
**团队规模：** 8 人，每人约 20 小时  
**迭代方式：** 一周 Sprint + DevOps，每周向客户展示可运行增量  
**本周版本：** `v0.1-thin-slice`

---

## 1. 第一周目标

第一周的目标是验证系统架构、数据接口和端到端技术链路，不追求完成全书处理或正式实验数据集。

本周需要跑通以下最小流程：

```text
OpenStax Physics 2–3 个章节
→ 文本解析与清洗
→ 500-token Chunking
→ Dense Embedding 与 FAISS 索引
→ 20–30 道 SciQ Physics 题
→ Evidence Alignment
→ Top-K Retrieval
→ LLM 固定 JSON 回答
→ 基础自动评估
```

### 本周硬性目标

- 完成 OpenStax Physics 2–3 个章节的可靠解析；
- 从 SciQ 中筛选 50–100 道 Physics 候选题，并整理出 20–30 道可用于 Pilot 的题；
- 对 20–30 道 Pilot 题执行自动 Evidence Alignment；
- 至少人工确认 10 道题的 gold evidence；
- 建立一套 500-token chunks；
- 使用一个 embedding 模型建立 FAISS Dense 索引；
- 至少完成 10–20 道题的端到端生成；
- 输出 Hit@K、MRR、Answer-choice Accuracy、JSON 成功率和 citation ID 有效率；
- 周五提供可以复现的 Staging Demo。

### Stretch Goals

以下任务只在主流程稳定后进行：

- 将 OpenStax 解析扩大到全书；
- 将 SciQ Physics 分类扩大到全量数据；
- 将自动 Alignment 扩大到 50–100 道；
- 将人工确认扩大到 20–30 道；
- 增加 300-token Chunking 对照版本；
- 增加 BM25 baseline；
- 生成完整的 Beginner、Intermediate、Advanced 三档对比样例；
- 起草按章节隔离的 Dev/Test 划分。

### 本周不做

- Restricted KG 和 KG Expansion；
- 正式 Test Set 实验；
- 多模型正式比较；
- 全量 Evidence Role 标注；
- C4 Level-Aware Reranking 正式实现；
- Abstention 阈值标定；
- Mini Quiz、成绩单入口和 topic-level profile。

## 2. 1 号：Leader／系统架构与集成

### 主要职责

负责系统架构、模块接口、主流水线、DevOps工作方式、代码集成和客户沟通。Leader需要参与架构和集成代码编写，不能只负责会议和任务分配。

### 本周工作内容

- 编写系统组件图、数据流图和端到端调用流程；
- 定义并冻结第一版核心数据接口，包括：
  - `OpenStaxDocument`
  - `Chunk`
  - `SciQQuestion`
  - `EvidenceAlignment`
  - `RetrievalResult`
  - `StudentProfile`
  - `GeneratedAnswer`
  - `EvaluationRecord`
- 确定 `document_id`、`chapter_id`、`chunk_id`、`char_start`、`char_end` 等公共字段；
- 搭建项目目录、配置管理、日志、错误处理和统一运行入口；
- 建立主流水线，使各模块可以使用模拟数据并行开发；
- 集成 OpenStax、SciQ、Chunking、Retrieval、Generation 和 Evaluation；
- 建立 Development 和 Staging 两套运行配置；
- Review 跨模块代码并解决接口冲突；
- 准备客户 Demo、指标摘要、风险清单和下周 Backlog。

### 最终交付物

- 系统组件图和数据流图；
- 核心数据接口说明；
- Architecture Decision Record；
- 可运行的端到端主流水线；
- 统一配置、日志和运行入口；
- Staging Demo；
- 客户周报、风险清单和下周 Backlog。

### 验收标准

- 其他成员可以依据接口独立开发；
- 至少一条真实问题可以经过全部模块；
- Demo不依赖某位成员手工修改路径或Notebook；
- 另一名成员可以依据README复现运行过程。

## 3. 2 号：OpenStax 数据工程

### 主要职责

负责 OpenStax Physics 教材的获取、版本记录、解析、清洗、章节化和原文追溯。

### 本周工作内容

- 确定并获取一本 OpenStax Physics 教材；
- 记录教材名称、版本、来源、下载日期、文件格式和 `document_hash`；
- 选择 2–3 个结构清晰、内容具有代表性的章节；
- 解析章节、标题、小节、正文和页码；
- 清理页眉、页脚、重复内容、乱码和明显断词；
- 保留稳定的原文字符位置；
- 人工抽查至少 10 个段落或小节；
- 记录公式、表格、图片说明和跨页内容的问题；
- 将标准化内容交付给 5 号生成 chunks。

### 最终交付物

- OpenStax Physics 原始教材及版本记录；
- 2–3 个章节的标准化语料；
- 教材解析程序；
- `document_hash` 和 `parser_version`；
- 解析质量抽查记录；
- 已知解析问题清单。

### 验收标准

- 解析结果能够稳定重复生成；
- 标题、章节和正文没有明显错位；
- 任意选取的原文片段可以通过字符位置重新定位；
- 输出符合 Leader 冻结的 `OpenStaxDocument` 接口。

---

## 4. 3 号：SciQ 数据工程

### 主要职责

负责 SciQ 数据标准化、Physics 学科筛选、候选题清理和初步章节映射。

### 本周工作内容

- 读取并保存 SciQ 原始数据；
- 标准化问题、四个选项、正确答案和 support；
- 建立 Physics 候选题筛选规则；
- 筛选 50–100 道 Physics 候选题；
- 人工抽查至少 20 道分类结果；
- 从候选题中整理 20–30 道用于本周 Pilot；
- 检查选项顺序和正确答案映射；
- 将 Pilot 题初步映射到 OpenStax 的 2–3 个试验章节；
- 记录明显不属于教材范围或学科边界不清的题。

### 最终交付物

- 标准化 SciQ 数据样例；
- 50–100 道 Physics 候选题；
- 20–30 道本周 Pilot 题；
- 学科筛选规则或程序；
- 分类人工抽查结果；
- Pilot题与OpenStax章节的映射草案；
- 异常题和边界题清单。

### 验收标准

- 每道题都有问题、四个选项、正确答案和 support；
- 正确答案可以稳定映射为 A/B/C/D；
- Pilot题确实属于Physics并与试验章节存在合理关联；
- 输出符合 `SciQQuestion` 接口。

## 5. 4 号：Evidence Alignment

### 主要职责

负责将 SciQ support 和问题对齐到 OpenStax 原文，为检索评估建立小规模可信 gold evidence。

### 本周工作内容

- 定义 `accepted`、`manual_review` 和 `unresolved` 三种状态；
- 使用 embedding 相似度寻找候选段落；
- 使用模糊字符串匹配或局部匹配精确定位原文；
- 对 20–30 道 Pilot 题执行自动 Alignment；
- 与 8 号共同人工审核至少 10 道题；
- 记录候选 chunk、匹配位置、confidence 和失败原因；
- 建立 `Unresolved Pool`；
- 与 2 号核对 char span 是否可以回到教材原文；
- 不得将无法对齐的题直接标为 unanswerable。

### 最终交付物

- Evidence Alignment 初始程序；
- 20–30 道自动 Alignment 结果；
- 至少 10 道人工确认的 gold evidence；
- question/support 到 OpenStax char span 的映射；
- `Unresolved Pool`；
- Alignment 成功、失败和待审核原因报告。

### 验收标准

- 人工确认题可以准确定位到教材原文；
- 自动结果和人工结果的状态明确区分；
- 失败原因可以被统计；
- 检索指标只在人工确认的 gold 子集上作为可信结果汇报。

---

## 6. 5 号：Chunking 与 Metadata

### 主要职责

负责将标准化教材切分为可检索 chunks，并保证章节信息和原文追溯不丢失。

### 本周工作内容

- 实现一套 500-token Chunking；
- 设计合理的 overlap；
- 为每个 chunk 生成唯一 `chunk_id`；
- 保留 `document_id`、`chapter_id`、source、正文和 char span；
- 写入基础 chapter/topic metadata；
- 检查空 chunk、重复 chunk、极短 chunk 和跨章节切分；
- 与 2 号共同抽查至少 10 个 chunk 的原文追溯；
- 为未来 Evidence Role 字段预留位置；
- 只有主版本稳定后才尝试 300-token 对照版本。

### 最终交付物

- 500-token Chunking 程序和配置；
- 2–3 个章节的完整 chunks；
- chunk metadata；
- Chunk数量、长度和章节分布统计；
- 原文追溯抽查结果；
- 可选的300-token对照版本。

### 验收标准

- 所有 chunk 都有唯一 ID 和章节信息；
- chunk 的 char span 可以回到标准化教材；
- 不存在明显的空 chunk 或跨章节混合；
- 输出可以直接被 6 号用于建立索引。

---

## 7. 6 号：Dense Retrieval

### 主要职责

负责 embedding、FAISS Dense 索引、Top-K Retrieval、检索缓存和基础检索指标。

### 本周工作内容

- 选择一个适合 Pilot 的 embedding 模型；
- 验证查询侧是否需要指令前缀；
- 为 2–3 个试验章节的 chunks 生成 embedding；
- 使用 FAISS `IndexFlatIP` 建立精确索引；
- 实现问题到 Top-K chunks 的检索；
- 输出 chunk ID、排名、分数和查询耗时；
- 缓存本周 Pilot 题的检索结果；
- 在人工确认的 gold 子集上计算 Hit@1、Hit@5、Hit@10 和 MRR；
- 收集至少两个成功案例和两个失败案例；
- 只有 Dense 主链稳定后才尝试 BM25。

### 最终交付物

- Embedding 和索引构建脚本；
- FAISS Dense 索引；
- Top-K Retrieval 模块；
- Pilot 题检索结果缓存；
- Hit@K、MRR 和查询耗时统计；
- 检索成功与失败案例；
- 可选的 BM25 初始版本。

### 验收标准

- 相同配置可以重复生成索引和检索结果；
- Top-K 输出符合 `RetrievalResult` 接口；
- 检索结果能够被 7 号直接用于 Prompt；
- 指标明确标注使用的人工确认样本数量。

## 8. 7 号：Student Profile、Prompt 与 LLM Generation

### 主要职责

负责最小学生画像、Prompt、LLM 接入、固定 JSON 输出和引用完整性。

### 本周工作内容

- 接入一个可用的 LLM；
- 建立最小 `StudentProfile` schema；
- 默认使用 `Intermediate` synthetic profile 跑完整流程；
- 准备 Beginner 和 Advanced 的简单对比样例；
- 实现问题、学生水平和 Top-K evidence 的 Prompt 组装；
- 固定输出格式：

```json
{
  "final_choice": "B",
  "explanation": "...",
  "citations": ["chunk_17"]
}
```

- 实现 JSON 解析、schema 校验和有限重试；
- 限制 citations 只能引用输入的 chunk ID；
- 完成至少 10–20 道题的端到端生成；
- 记录模型、温度、token 使用量和失败类型。

### 最终交付物

- LLM 生成适配器；
- 最小 Student Profile schema；
- Intermediate 主流程配置；
- Beginner 和 Advanced 对比样例；
- Prompt 模板；
- JSON schema 和解析器；
- 10–20 道生成结果；
- JSON、引用、失败和 token 使用统计。

### 验收标准

- 输出可以稳定解析为固定 JSON；
- citation ID 来自实际输入的 chunks；
- 生成模块可以接受 6 号的真实检索结果；
- 单个API失败不会使整个批次终止。
