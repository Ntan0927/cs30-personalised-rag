# CS-30 第一周分工安排（不含正式评估）

**团队规模：** 8 人，每人约 20 小时  
**本周版本目标：** `v0.1-thin-slice`  
**工作方式：** 一周 Sprint + DevOps，周五向客户展示可运行版本

---

## 1. 第一周共同目标

第一周只验证端到端技术链路，不进行正式研究评估。需要跑通：

```text
OpenStax Physics 2–3个章节
→ 教材解析和清洗
→ 500-token Chunking
→ Embedding和FAISS索引
→ Dense Top-K Retrieval
→ Student Profile
→ Personalised Prompt
→ LLM固定JSON回答
→ 简单演示界面
```

### 本周必须完成

- 可靠解析 OpenStax Physics 的 2–3 个章节；
- 从 SciQ 中整理 20–30 道 Physics 演示问题；
- 生成一套带章节和来源信息的 500-token chunks；
- 使用一个 embedding 模型建立 FAISS Dense 索引；
- 输入问题后能够返回 Top-K chunks 和教材来源；
- 支持 Beginner、Intermediate、Advanced 三档学生水平；
- 至少 10–20 道问题可以生成固定 JSON 回答；
- 回答中的 citation ID 必须来自实际检索结果；
- 提供统一运行入口和简单演示界面；
- 周五可以在 Staging 环境向客户现场演示。

### 本周不做

- Evidence Alignment 正式流程；
- gold char span 标注；
- Hit@K、Recall@K、MRR；
- Answer-choice Accuracy；
- 正式 Dev/Test 划分；
- Evidence Role 标注；
- BM25 和 RRF 正式比较；
- Abstention 校准；
- Restricted KG；
- 多模型正式对比。

### 工程检查不属于正式评估

本周仍需要进行以下基本工程检查：

- 系统能否启动；
- 数据接口能否正确读取；
- 索引能否建立和加载；
- Retrieval API 能否返回结果；
- LLM 输出能否解析为固定 JSON；
- citation ID 是否存在于检索结果中；
- 另一名成员能否按照 README 运行系统。

这些检查只用于保证系统可运行，不用于证明模型或检索方法效果更好。

## 2. 1号：Leader／系统架构与集成

### 负责方向

- 定义并冻结第一版核心接口：
  - `OpenStaxDocument`
  - `Chunk`
  - `SciQQuestion`
  - `RetrievalResult`
  - `StudentProfile`
  - `GeneratedAnswer`
- 确定 `document_id`、`chapter_id`、`chunk_id`、`source`、`char_start` 和 `char_end` 等字段；
- 搭建统一项目目录、配置、日志和错误处理；
- 建立端到端主流水线；
- 为未完成的模块提供 Mock / Fixture 数据；
- 持续集成 2–8 号的模块；
- Review 跨模块代码并解决接口冲突；
- 准备周五客户 Demo、周报、风险清单和下周 Backlog。

### 最终交付物

- 系统组件图和数据流图；
- 核心数据接口说明；
- Architecture Decision Record；
- 可运行的端到端主流水线；
- 统一配置、日志和启动入口；
- Staging Demo；
- 客户周报、风险清单和下周 Backlog。

### 完成标准

- 所有模块使用同一套接口；
- 至少一条真实问题能够经过完整流水线；
- Demo 不依赖手工修改路径或临时 Notebook；
- 另一名成员可以依据 README 复现运行。

## 3. 2号：OpenStax 数据工程

### 负责方向

负责 OpenStax Physics 教材获取、版本记录、文本解析、清洗和章节化。

### 具体工作内容

- 确定并获取一本 OpenStax Physics 教材；
- 记录教材名称、版本、来源、下载日期、文件格式和 `document_hash`；
- 选择 2–3 个适合作为第一周演示的章节；
- 解析章节、标题、小节、正文和页码；
- 清理页眉、页脚、重复内容、乱码和明显断词；
- 保留稳定的文本位置，支持 chunk 返回教材原文；
- 人工检查至少 10 个段落或小节；
- 记录公式、表格、图片说明和跨页文本问题；
- 先向 4 号交付一个可用章节，再继续完成其他章节。

### 最终交付物

- OpenStax Physics 原始教材及版本记录；
- 2–3 个章节的标准化语料；
- 教材解析程序；
- `document_hash` 和 `parser_version`；
- 解析质量抽查记录；
- 已知解析问题清单。

### 完成标准

- 相同输入能够重复生成相同的标准化文本；
- 章节、标题和正文没有明显错位；
- 标准化文本能够被 4 号直接用于 Chunking；
- 任意演示 chunk 可以定位回教材原文。

- 准备 5–10 道适合客户现场输入的自由问答问题；
- 与 7 号共同确认问题格式能够进入 Prompt；
- 本周题目只用于 Smoke 和 Demo，不作为正式 Test。

### 最终交付物

- 20–30 道标准化 SciQ Physics 演示题；
- SciQ 问题读取和转换程序；
- 题目、选项、答案和 support 的统一格式；
- 5–10 道自由问答演示问题；

### 完成标准

## 5. 4号：Chunking与Metadata

### 负责方向

负责将标准化 OpenStax 文本转换成可检索 chunks，并保留教材来源和章节信息。

### 具体工作内容

- 实现 500-token Chunking；
- 设计合理的 overlap；
- 为每个 chunk 生成唯一 `chunk_id`；
- 保留 `document_id`、`chapter_id`、source、正文和 char span；
- 写入基础 chapter/topic metadata；
- 检查空 chunk、重复 chunk、极短 chunk 和跨章节切分；
- 与 2 号共同验证至少 10 个 chunk 的原文追溯；
- 先提供约 20–50 个样例 chunks 给 5 号开发索引；
- 主版本稳定前不做 300-token 对照实验。

### 最终交付物

- 500-token Chunking 程序和配置；
- 2–3 个章节的完整 chunks；
- 完整 chunk metadata；
- Chunk 数量、长度和章节分布统计；
- 原文追溯样例；
- Chunking 已知问题清单。

### 完成标准

- 所有 chunk 都有唯一 ID 和章节来源；
- chunk 文本可以定位回标准化教材；
- 不存在明显的空 chunk 和跨章节混合；
- 输出能够被 5 号直接用于 embedding 和索引构建。

---

## 6. 5号：Embedding与FAISS索引

### 负责方向

负责 embedding 模型接入、chunk 向量生成、FAISS 索引构建和索引持久化。

### 具体工作内容

- 选择一个适合第一周 Pilot 的 embedding 模型；
- 检查查询侧是否需要固定指令前缀；
- 为 chunks 批量生成 embeddings；
- 对向量进行与检索方案一致的归一化；
- 使用 FAISS `IndexFlatIP` 建立精确索引；
- 建立 `chunk_id` 与向量位置的映射；
- 实现索引保存、加载和版本记录；
- 记录 embedding 模型、维度、运行设备和构建时间；
- 先使用 4 号的样例 chunks 建立小索引，再替换为真实章节数据；
- 与 6 号确认索引调用接口。

### 最终交付物

- Embedding 生成程序；
- FAISS 索引构建程序；
- 2–3 个章节的 Dense 索引；
- `chunk_id` 映射文件；
- 索引保存和加载功能；
- 模型、配置、维度和构建时间记录；
- 索引使用说明。

### 完成标准

- 相同语料和配置可以重复构建索引；
- 保存后的索引可以重新加载；
- 加载索引后能够返回对应 `chunk_id`；
- 6 号可以通过固定接口使用索引。

## 7. 6号：Dense Retrieval与Backend API

### 负责方向

负责将用户问题转换为查询向量、检索 Top-K chunks，并通过统一 Backend API 提供给生成模块。

### 具体工作内容

- 实现问题预处理和查询 embedding；
- 调用 5 号的 FAISS 索引；
- 实现 Top-K Dense Retrieval；
- 返回 `chunk_id`、文本、章节、来源、分数和排名；
- 封装 Retrieval API 或统一 Python service；
- 实现索引缺失、空问题和无结果时的错误处理；
- 缓存本周演示问题的检索结果；
- 准备至少两个检索结果合理的演示案例；
- 与 7 号确认 `RetrievalResult` 输入输出；
- 在真实索引完成前，先使用模拟索引或固定 chunks 开发 API。

### 最终交付物

- Top-K Dense Retriever；
- Retrieval Backend API；
- API 输入输出说明；
- 检索结果缓存；
- 错误处理和日志；
- 真实演示问题的 Top-K 输出样例；
- 与生成模块的连接代码。

### 完成标准

- 输入问题后能够稳定返回 Top-K chunks；
- 返回结果包含教材来源和 chunk ID；
- 7 号能够直接使用返回结果构建 Prompt；
- 索引或输入异常时返回明确错误，而不是使整个系统退出。

## 8. 7号：Student Profile、Prompt与LLM Generation

### 负责方向

负责学生画像、个性化 Prompt、LLM 接入、固定 JSON 输出和 citation 完整性。

### 具体工作内容

- 接入一个可用的 LLM；
- 建立最小 `StudentProfile` schema；
- 支持 Beginner、Intermediate 和 Advanced 三档水平；
- 实现问题、Student Profile 和 Top-K evidence 的 Prompt 组装；
- 固定输出格式：

```json
{
  "final_choice": "B",
  "explanation": "...",
  "citations": ["chunk_17"]
}
```

- 实现 JSON 解析、schema 校验和有限重试；
- 限制 citations 只能引用输入的 chunk ID；
- 处理 API 超时、空响应和非法 JSON；
- 完成至少 10–20 道问题的端到端生成；
- 准备同一道题在三个水平下的回答样例；
- 记录模型、温度、token 使用量和失败类型；
- 在 6 号完成前，使用固定 `RetrievalResult` fixture 开发。

### 最终交付物

- LLM 生成适配器；
- Student Profile schema；
- Beginner、Intermediate 和 Advanced 三档配置；
- Prompt 模板；
- 固定 JSON schema 和解析器；
- 至少 10–20 道生成结果；
- 三档回答对比样例；
- citation、失败和 token 使用记录。

### 完成标准

- 输出能够稳定解析为固定 JSON；
- citation ID 来自实际检索输入；
- 三档水平能够进入 Prompt；
- 单次 API 失败不会导致整个批次终止。

## 10. 协作组合与依赖处理

| 协作组合 | 成员 | 共同负责 |

| 教材处理组 | 2号 + 4号 | OpenStax解析、Chunking、Metadata和原文追溯 |

### 防止等待的规则

- 2号先交一个章节，4号即可开始Chunking；

- 5号先交小型索引，6号即可开发Retriever；
- 6号未完成时，7号使用固定RetrievalResult开发；
- 后端未完成时，8号使用Mock数据开发界面；
- 周五不是第一次集成，主分支在本周内持续保持可运行。
